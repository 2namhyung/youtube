# Portable project backup and copy restore

Provide a portable ZIP containing a current planning project and all its referenced local assets, recordings and byte-verification receipts. Restore into a new planning project without overwriting the original or importing production authority. Existing JSON import/export behavior remains unchanged.

## Archive contract

Version `visualmaker-project-backup-v1` includes a strict manifest, `plan.json`, exact content-addressed bytes for every `plan.assets` and `plan.narrationTakes` record, and their matching receipts, including inputs not currently assigned to a requirement. The manifest binds source project/revision, false production authority, Plan byte count/SHA-256, and every file path/byte count/SHA-256. Media shared by multiple records appears once; all required receipts remain included, and shared requirement references remap to the same new asset ID. Script revision history in the Plan is retained. Database files, project revision tables, AI jobs/attempts/artifacts, render results, external source archives, application config and production artifacts are excluded. This is a portable current-project snapshot, not a database clone or full machine backup.

Produce ordinary ZIP entries with method STORE; compressed media need not be recompressed. The portable format accepts only the specified entry layout and supported ZIP encoding, not arbitrary third-party archives. Reject unsupported compression/encryption, ZIP64, multi-disk, symlinks, duplicate names, absolute/drive/UNC/backslash/traversal paths, malformed local/central headers, overlaps, CRC mismatch, missing/extra entries, changed receipts, hash/size mismatch, invalid Plan or authority. Do not extract using caller-provided filesystem paths.

Explicit bounded limits: archive <=128 MiB, <=512 entries, each media <=50 MiB, total entry payload <=120 MiB, each manifest/receipt <=256 KiB and Plan <=3 MiB. Reject over-limit requests before allocating or processing more bytes; bounds apply to headers and actual bytes. Fail rather than silently omitting a referenced input. Exports with missing or changed referenced media/receipts fail. These limits must be visible in the subsequent UI.

Read export inputs through verified, non-linked regular file handles and retain the exact validated bytes. Reject symbolic links/junctions and hardlinked media/receipts (`stat.nlink !== 1`); check opened file-descriptor identity and file metadata before/after reads. Apply the same linked-file/identity policy to existing destination content-addressed files before reusing them. Validate containment and all ancestor paths; hash checks alone do not authorize reading an outside file or `.env` through a linked receipt path. Check the requested current revision before and after collection and reject concurrent scope change. Export does not mutate the Plan or create a job.

## Restore contract

Authenticate and validate the entire bounded archive before materialization. Revalidate original Plan and its byte/metadata receipts, then transform it into a new copy with new project, asset and recording IDs. Rebind every requirement asset reference and all retained recording/timing references; preserve original raw script/history, beats, scenes, direction choices/locks, timing estimates, source URL/creator/rights/semantic notes, evidence-only flags and the actual media bytes. No record may be lost solely because the destination is empty.

Clear source-review approvals, local episode `Plan.origin` and scene `originCutIds`, the local AI analysis adoption receipt, and paired timing `manualReviewConfirmed`/`manualReviewConfirmedAt` fields, which require local context, job provenance or human listening attestations. Preserve the original provenance in the archived source Plan rather than pretending imported metadata is verified local acquisition. Keep the source Plan revision and coherent capture-revision numbers in the new copy; do not force revision 1 or fabricate earlier database revision rows. The new project has exactly one initial database revision snapshot. Script history and historical/current timing bindings must still pass the current validator.

Archived receipts and hashes prove internal byte consistency, not a trusted local measurement. Restore must decode visual media and remeasure recordings with the existing sharp/ffprobe validation path before generating fresh receipts. Reject differences in declared media type, dimensions, duration, sample rate or channels, and preserve evidence-only classification. Any retained recording/timing remains draft/non-production. Production authority is always false. Return a summary of retained inputs and cleared review/provenance records for explicit UI disclosure.

Stage files only under an owned, canonical data-root subdirectory, with exclusive creation and no link traversal. Publish content-addressed media only when absent; an existing exact byte match may be reused, while mismatched files or linked paths cause failure. New receipt names are unique to new IDs. Insert the new Plan and its initial immutable revision in one transaction only after all required inputs are valid and materialized. On failure, no project/revision is added and existing bytes/documents are unchanged. Cleanup may remove only exact files created by that operation; crash leftovers must never imply a completed restoration. Do not claim filesystem and SQLite commit are one atomic operation.

## Authenticated API

`GET /api/studio/backup?projectId=…&baseRevision=…` requires the existing session guard, strict project/revision arguments, and returns `application/zip`, bounded Content-Length, safe attachment filename and `Cache-Control:no-store`. Stale scope returns 409; invalid/missing/unsafe inputs fail closed without returning partial data.

`POST /api/studio/backup` accepts the ZIP bytes with `Content-Type:application/zip` and explicit `x-visualmaker-restore-copy:1`, in addition to the existing mutation origin/token guard. Enforce a streamed byte bound, not only Content-Length. Restore is new-copy only: no target project ID, destination path, overwrite or approval option. Success is 201/no-store `{plan,summary}`. All errors are no-store; oversized input is 413, malformed input 400, integrity/path conflicts reject without state mutation. No automatic retry after an uncertain save.
