# User reviewed AI analysis adoption into planning

Let users select exact source-bound analysis records and explicitly apply their core message to unlocked planning beats. Keep all five analysis fields and the exact proposal provenance in a planning-only receipt. This operation does not edit the script, select production modes, acquire sources, approve claims/rights/grammar, or write episode production files.

## Frozen request and response

Dedicated authenticated POST `/api/studio/ai-analysis-adoption` accepts exactly `{projectId,baseRevision,jobId,expectedArtifactSha256,segmentIds,confirmDirectionReset:true}`. IDs/revision/hash use existing strict validators; segment IDs are unique, nonempty, <=40 and in proposal order. The caller sends no generated content, paths, mode, role, approval flags or arbitrary command. Reject missing/extra fields and wrong consent. Readiness/configuration for a new external call is not required to adopt an already validated current successful result. No provider request, enqueue, run or retry occurs.

Return HTTP 200/no-store `{plan,adoption}` where `adoption` is the exact persisted planning receipt. All error responses are no-store. Stale revision/snapshot/proposal/hash is 409; any selected beat participating in a locked scene is 423 and the whole request rolls back. Unknown/ambiguous segment-to-beat/scene mapping is rejected; do not guess or silently skip. An uncertain successful response retry cannot apply twice: the old base revision is rejected, and the receipt can be retrieved with the current Plan. Do not invent idempotent success based only on job ID.

## Atomic source and planning checks

Use one `BEGIN IMMEDIATE` transaction to read current project revision/normalized Plan, verify the original succeeded AI job/checkpoint/artifact bytes and full current-scope proposal, resolve all selected segment bindings, preflight every owning scene lock and then write one project revision plus its immutable revision-history row. Reuse the bounded artifact reader, strict proposal validation and current-snapshot hashes from `readAIProposal`; if needed factor a shared transaction-aware reader without weakening existing GET behavior or opening a second writable DB while the lock is held. Initialize AI schema before taking the transaction. No check-before-transaction snapshot may authorize later writes without rechecking inside.

Only singleton beat-to-segment and exactly one owning scene mappings are adoptable in this slice; merged/ambiguous mappings are explicitly unavailable, not fanned out. Preserve each beat role. `mainMessage` becomes `Beat.intent` using existing edit-beat semantics, so changed intent rebuilds draft direction candidates/requirements and clears selected direction. The explicit reset acknowledgement covers this effect; preserve scene timing, origin linkage, unrelated scenes, actual asset bytes, script revisions/narration and all locked scenes. If multiple selections belong to one scene, reject rather than repeatedly rebuilding. Apply the batch with exactly one revision increment, not sequential store updates. All selection/preflight failures must leave document and revision history unchanged.

## Planning receipt

Add optional `Plan.aiAnalysisAdoption` representing the latest adoption, preserving the historical receipt in existing immutable project revision snapshots. Client-safe type is version `visualmaker-ai-analysis-adoption-v1`, with server-generated ID/time, job ID, artifact SHA-256, original proposal scope/model, before/after Plan revisions, script SHA-256, `productionAuthority:false`, `requiresHumanReview:true`, and ordered selected records. Each selected record binds segment/beat/scene IDs, exact source start/end/text/kind, all five original proposal strings, before intent and applied intent. No user or production PASS is represented; applying a message is an editorial action, not certification of generated assertions or translation. Exact receipt serialization/size is bounded to <=200000 bytes and selections <=40. Keep original AI values unchanged in the receipt; subsequent manual editing does not rewrite it.

`validatePlan` must validate and preserve this optional record, including revision/order/unique IDs, field bounds, source code-point/hash bindings to the recorded script (use retained script history for stale receipts), and false authority flags. Historical script entries retain raw text/hash, not old segment kind/ID or beat/scene mappings: historical parsing revalidates source spans/text/hash only; exact mapping is verified at local creation and preserved in immutable project revision snapshots. Do not require current job files when parsing a historical Plan. Source/beat/scene references may become historical after later edits; label them stale via revision/script comparison rather than dropping the record or blocking normal script edits. Project-copy import clears the receipt so imported JSON cannot fabricate local adoption provenance. Historical receipt means supplied metadata only unless the local API created it; no renderer/source validator treats it as approval. No new generic `Command` may let public PATCH manufacture an AI receipt; adoption uses only the dedicated verified route.
