## API and response contract

Use the exact authenticated POST request and persisted receipt defined in [the backend contract](AI-ANALYSIS-ADOPTION-TASK.md). Send only project ID, base revision, job ID, expected artifact SHA-256, selected segment IDs in proposal order, and `confirmDirectionReset:true`. Adoption must not enqueue, run or retry AI jobs. It remains available for a verified current successful result even when new provider calls are unavailable.

The browser must validate the bounded response before installing it: project ID, exactly one revision increment, unchanged script and false production authority; the returned receipt equals `plan.aiAnalysisAdoption` and binds the original job, artifact, proposal scope/model and ordered selected records. Each record must match the reviewed original five strings, source span/text/kind, singleton segment/beat/scene mapping, previous intent and applied intent. Reject malformed or mismatched authority, scope, hashes, mappings and records. Preserve script/history, assets, narration, roles, timing and unrelated scenes; selected scenes may change only through the contracted draft direction reset. Do not import Node-dependent server modules into browser code.

Coordinate adoption with the parent Studio mutation boundary. Prevent concurrent local planning writes while the request is active; guard against rapid double submission with an immediate ref, not only asynchronous state. Scope-check the response against the current project/revision/script/token and abort on unmount. Install a validated successful Plan once, clearing old proposal, selections and acknowledgements through the existing keyed panel. Do not retain source review states as though rebuilt requirements still have the previous bindings; clear stale states and refresh the current report through the existing GET route where needed. A failed optional list refresh after successful persistence must be reported separately, never as a failed save.

The parent mutation gate must acquire a synchronous shared ref or equivalent lock before starting adoption or another planning write; the current React `busy` state alone does not exclude same-event races. In the AI panel, reuse the immediate action boundary for adoption and existing enqueue/run/cancel/recover actions: while either kind of action is active, the other cannot start. Block all AI command controls during adoption and block adoption during any active AI action. A revision fence cannot undo an external call or charge that has already started.

Child writes use stable `beginMutation(): (()=>void)|null` before their POST. A null result prevents starting; a successful operation owns its idempotent release closure and releases only that ownership on completion or cleanup. A stale child must not clear another owner's busy state. Stable callbacks and primitive effect dependencies must not abort the request on ordinary parent rerender. Read-only search, reports and playback do not acquire the Plan-write gate.

Browser draft validation mirrors the current deterministic director projection without importing its Node-dependent module. Differential tests must compare real server handler output across all four draft mode families and reject altered candidate or requirement fields. Shared asset requirements may legitimately receive new pending source reviews in unselected scenes when their sharing context changes; validate the actual before/after context SHA, asset binding and three review dimensions instead of restricting every new review to a selected scene. Keep the existing review history unchanged. The mirrored projection is version-coupled; future director changes require the differential tests and browser projection to be updated together.

No automatic resubmission follows an uncertain response, abort or network failure. Explain that the user must reload the current project to check the persisted receipt before deciding what to do next. Old-base retry is not an idempotent success route. A conflict cannot install an older response over a newer Plan.

## Review controls

Show each exact original source passage, existing intent and proposed core message beside the four retained review notes. Checkboxes are individually labelled, initially unchecked, and enabled only for unambiguous unlocked singleton mappings. Explain why locked or merged/ambiguous rows are unavailable; never silently skip them. Preserve proposal order when building the selection.

Require a separate acknowledgement that changing selected messages rebuilds draft direction candidates and requirements and clears selected directions. Disable save with no selection, without that acknowledgement, while loading or busy, or without a current verified proposal/job/artifact. Do not add automatic select-all or automatic adoption. State that all desired rows must be selected before saving: the one revision increment makes the original snapshot stale, so remaining rows from that job cannot subsequently be adopted unchanged.

After saving, show the persisted adoption receipt separately from active AI proposals. Label it as planning history, with original and applied messages, retained notes and provenance. Revision/script mismatch is historical or stale, not a current approval. Applying a message does not certify its factual accuracy or grant source, rights, grammar, visual or production PASS. A receipt with `sdk-test` provenance is visibly synthetic and cannot be presented as actual model quality evidence.
