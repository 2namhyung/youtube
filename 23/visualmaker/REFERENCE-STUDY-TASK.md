# YouTube reference study foundation

## Objective and ownership

User priority: reproduce the screen composition, motion and editing language of a supplied YouTube video in VisualMaker, then improve the independently implemented result. This slice implements only a pure, non-production study contract, not remote video analysis, downloading, rendering, persistence or UI.

One implementation writer owns `visualmaker/core/reference-study.ts`, `tests/visualmaker-reference-study.test.mjs`, the focused test command in `package.json`, and a clearly labelled capability section in `visualmaker/README.md`. Preserve all existing edits. No redelegation, commit or push.

Forbidden writes: raw, wiki, video, production files/approval markers/generated files, database/user assets, other worktrees, existing plan authority/model. No network requests, dependencies, real media creation or fabricated observations.

## Contract

- A separately versioned `visualmaker-reference-study-v1` draft records an explicit YouTube URL/video ID, objective and stable caller-supplied study ID. Canonicalize supported exact YouTube hosts and watch/shorts/embed/youtu.be forms using URL parsing. Reject spoof hosts, credentials, unsupported schemes, malformed IDs, playlists without a single video, and sensitive/tracking parameters in the stored canonical URL. Canonical URL retains only video identity; time windows are explicit study fields. No URL fetching or arbitrary URL execution.
- A study starts with zero observed segments and visibly blocked analysis. Capabilities must explicitly declare automatic analysis, remote access, rendering and production authority unavailable/false.
- Observations bind to explicit finite nonnegative start/end seconds (end > start), a precise evidence locator (local still/frame/timecode declaration, safe relative POSIX path and non-placeholder SHA-256 when claimed), and nine dimensions: stage, focal, supporting, depth, entrance, internal-change, transition, hold, exclusions. Every dimension is either an observed nonblank note linked to evidence IDs or explicitly unknown/not-applicable with a nonblank reason. Motion must cite frame/timecode evidence across at least two distinct times; a still alone cannot prove motion. Missing evidence remains blocked, not generated from the URL. Paths reject NUL, absolute, drive, UNC, backslash, empty, dot, and traversal segments; placeholder matching is by exact filename stem only.
- Record borrowed elements, excluded elements and original-subject replacement intent separately. Do not reuse source video pixels/media as production assets or treat this study as a factual/rights source.
- Tool-gap records are separate from the source video's reproduction observations. Each gap binds a target observation (or explicitly says the gap is not yet tied to an observation), required VisualMaker behavior, current tool limitation, evidence or an explicit unknown reason, and a testable acceptance criterion. Its basis must distinguish `observed` from `hypothesis`. An `observed` gap requires target-observation source evidence IDs, typed reproduction/probe evidence locators (kind, media type, relative path, declared SHA-256 and time), paired source/reproduction timepoints, and an explicit comparison note describing the observed difference. Source-frame observations alone cannot support an observed VisualMaker limitation. Evidence IDs from a different observation are rejected. A hypothesis requires an explicit unknown-comparison reason; a missing or invalid observed comparison is invalid rather than silently downgraded. Hashes are declarations only: local bytes remain unverified. A separate capability-upgrade proposal may address that tool gap. It must not change, reinterpret, or “improve” the source video's observed grammar. New grammar stays unapproved and cannot be auto-promoted. No approval, style-frame eligibility, cut PASS, episode-spec writes or compatibility claims with historical schemas/contracts.
- Functions create a draft, validate imported unknown data fail-closed, and produce an honest readiness report (structural validation only, local bytes not verified, human review required, no automatic reference-fidelity PASS). Never mark actual byte verification from hashes alone. Prefer JSON-serializable client-safe code with no fs/network/crypto side effects.
- Avoid arbitrary minimum sample counts. Evidence requirements follow each claimed observed dimension; unknown dimensions and zero segments must remain valid drafts but blocked for calibration.

## Completion and verification

Use existing style and Node strip-types compatible TypeScript. Focused tests cover URL variants/security, empty draft, malformed/unexpected authority fields, malformed time windows/dimensions/evidence references, relative path safety, still-only motion blocked, time-bound motion declarations, source-only/cross-observation/unpaired comparison rejection, separate tool-gap/capability-upgrade proposals (without modifying source observations), no mutation of inputs, and no production eligibility even for complete declared study. Record explicit limitations in README.

Run `pnpm run visualmaker:check` (baseline 51 tests), `git diff --check`. An independent execution verifier and reviewer follow the writer. No browser/API claims: this slice is core-only, to be wired into a reference workspace next.
