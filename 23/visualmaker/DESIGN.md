## 0. 결론

`reaink/script2video`는 초기 웹 인터페이스와 제공자 연결 구조의 포크 출발점으로 사용한다. 그러나 그 프로젝트의 `Shot`에 화면 종류 몇 개를 추가하는 방식으로 핵심 제품을 만들지는 않는다. 새 `/studio` 작업 화면과 독립된 편집 데이터 모델을 만든다. 다른 저장소는 통째로 합치지 않고 원문 보존, 승인, 작업 상태, 템플릿 규칙처럼 특정 설계만 참고한다.

제품 목표는 **대본을 넣으면 사람이 채택·수정할 수 있는 화면 대안이 나오고, 실제 확보 가능한 소스와 재사용 가능한 그래픽을 연결하여 장면표를 확정하는 것**이다. 초기에 AI가 모든 컷을 생성하거나 완성 영상을 자동 납품하는 것은 목표가 아니다.

사용자가 확정한 방향은 내레이션 중심의 실사·자료·카툰·모션그래픽 혼합, 낮은 제작 부담, 장면 재사용, 사용자의 직접 수정이다. 초기 설치 형태는 별도 요구가 없으므로 **1인용 로컬 웹앱**으로 가정한다. 여러 사용자 SaaS, 모바일 단독 편집, 클라우드 렌더링은 후속 범위다.

실제 참고 영상은 이번 검토에서 확보하지 못했다. 특정 채널의 컷 길이·색·전환 문법을 관찰한 결과가 아니라 대화에서 정의한 요구에 대한 설계다.

## 1. 조사 범위와 이전 판단의 수정

GitHub 연결 도구로 실제 파일을 읽고, 외부 제공자·렌더러의 공식 문서를 확인했다. 핵심 파일·증거는 `RESEARCH.md`에 기록했다. 실행 환경에서 공개 저장소를 clone하려는 시도는 DNS 해석 실패로 끝났다. 따라서 원본 앱의 설치·빌드·UI·한국어 생성 품질·외부 API 성공 여부는 검증하지 않았다. 이 패키지에서 실제 실행한 검사는 직접 작성한 제안 규격과 합성 예시에 대한 23개 단위 테스트다.

다음 판단을 수정한다.

- Script2video에는 이미 생성과 검토의 두 번 모델 호출이 있다. 단순히 2-pass로 나눈다는 설명만으로는 새 제품의 차별점이 되지 않는다. 개선점은 의미 분석, 표현 후보, 소스 확인, 승인, 확정 렌더 계획 사이에 명확한 규격을 두는 것이다. [S2]
- Showrunner에는 실제 `estimateCost` 함수가 있다. 새 설계는 비용 추정 자체를 처음 추가하는 것이 아니라 기존 자산 재사용, 사람의 편집 부담, 승인된 지출 한도를 함께 다룬다. 저장소에 적힌 모델 단가는 현재 실제 가격으로 재사용하지 않는다. [S6]
- Script2video의 export 파일 상단에는 오디오 미보존 설명이 있지만, 현재 함수 안에는 오디오 디코딩·믹싱 코드가 있다. 상단 주석만 근거로 무음 출력이라고 단정하지 않는다. 한계는 실시간 브라우저 녹화 방식, 음성과 독립적인 자막 균등 배분, 정식 다층 편집 타임라인의 부재다. [S3]
- Remotion 엔진은 MIT 라이선스가 아니다. 해당 엔진의 자체 사용 조건과, 이를 이용하는 프로젝트의 라이선스는 따로 확인한다. 공식 문서의 v5 약관은 확인 시점에 Upcoming으로 표시되어 있다. [S14, S15]
- 공개 저장소를 포크하는 데 원본 저장소 push 권한은 필요하지 않다. GitHub의 공개 포크는 공개 저장소 네트워크에 속하므로 비공개 제품 개발이 필요하면 MIT 고지 등을 보존한 별도 저장소 방식도 검토한다. [S1, S16]

## 3. 제품의 한 문장과 성공 조건

“무슨 화면을 넣을지 고민하는 시간을 줄이되, 왜 그 화면인지와 실제 제작 방법을 사용자가 통제할 수 있는 장면 설계 작업대.”

완료 산출물은 글이 많은 표 하나가 아니다. 각 장면에 원문 연결, 전달 목표, 선택한 시각 처리, 대안, 시작/변화/끝, 필요한 소스, 실제 자산 연결, 근거·이용 조건 상태, 임시 또는 확정 시간, 승인 기록이 있어야 한다.

성공 지표는 자동 생성 컷 수보다 **승인 가능한 장면표까지의 사람 작업량**이다. 첫 제안 채택률, 승인까지의 직접 편집 시간, 장면당 수동 검색 횟수, 재사용 채택 수, 검토가 필요한 주장 중 근거가 연결된 비율, 재시도 비용을 기록한다. 감소율·정확도 목표는 실제 기준선을 측정하기 전에는 단정하지 않는다.

## 4. 사용자 흐름

### 4.1 대본을 넣고 발화 대본을 확인한다

원본은 변경 불가능한 `ScriptRevision`으로 저장한다. 내레이션과 연출 메모·참고 URL을 분리하고 사용자가 발화 구간을 확인한다. LLM이 내레이션을 다시 써서 돌려주는 대신 `segmentIds`를 반환하고 서버가 원문에서 텍스트를 채운다.

직접 대본을 고치거나 AI 수정안을 채택하면 **새 리비전**을 만든다. 이전 원문을 덮어쓰지 않는다. 원문 충실성은 사실 정확성을 대신하지 않는다. 잘못된 원문 주장은 별도 근거 검토가 필요하다.

### 4.2 의미 단위와 장면을 구분한다

한 문장마다 반드시 컷을 바꾸지 않는다. 먼저 설명하려는 핵심 의미 단위인 `Beat`를 만든다. 여러 문장이 하나의 비교 화면에 들어갈 수 있고, 긴 문장을 두 의미 단위로 분리할 수도 있다. 원문 구간은 중복·누락 없이 추적한다. 의도적 재배열·반복은 별도 편집 결정으로 기록한다.

### 4.3 표현 대안을 나란히 고른다

장면마다 기본 두 가지, 필요한 경우 세 가지 안을 제시한다. 단순히 색상만 다른 안이 아니라 실사+설명 그래픽, 순수 도식, 카툰 비유처럼 설명 전략이 다른 안을 만든다. 전달 목표를 만족하는 안 사이에서 사람 작업량과 신규 자산 수를 비교한다.

각 안에는 ‘왜 적합한가’, ‘어떤 재료가 필요한가’, ‘지금 존재하는 템플릿인가’, ‘실제 소스가 확보됐는가’, ‘어디까지가 예시인가’를 표시한다. 소스가 없는 안도 구상 단계에서는 허용하지만 준비 완료로 표시하지 않는다.

### 4.4 소스를 못 찾으면 대본과 화면을 함께 다듬는다

예를 들어 “서로 다른 여러 앱을 동시에 확인하는 사람”의 실사 확보가 어렵다면, 일반적인 스마트폰 컷 위에 서비스 카드를 띄우는 대안을 낸다. 그래도 설명이 불분명하면 내레이션 표현 수정안을 diff로 제안한다.

원문의 수치·단위·기간·대상·부정어·예외 조건을 자동으로 없애서는 안 된다. 사실의 변경을 수반하는 제안은 별도 근거 확인 대상으로 표시한다. 그래프의 출처가 없다는 이유로 관련 스톡 화면을 붙인 뒤 ‘근거 확보’ 상태로 바꾸지 않는다.

### 4.5 미리보기에서 타이밍을 확인하고 확정한다

그래픽 완성 전에 저비용 템플릿·정지 그림과 임시 음성으로 장면을 재생한다. 글을 읽을 시간, 강조어와 변화 시점, 실사와 도식의 연결을 확인한다. 원고가 바뀌면 해당 음성·타이밍만 미완료로 되돌린다.

## 5. 화면 구조

상단: 프로젝트 제목 / 대본 리비전 / 화면비 / 스타일 / 예산 / 미해결 항목 수 / 내보내기.

왼쪽: 대본 편집기. 문장을 선택하면 대응 장면을 강조한다. 근거가 필요한 주장에는 표시를 둔다. 승인 대본과 수정 제안은 다른 표시를 사용한다.

가운데: 장면표. 축약 기본 열은 순서, 내레이션, 전달 목표, 선택안 썸네일, 소스 상태, 길이, 승인이다. 장면 선택 시 상세 설명을 펼친다.

오른쪽: 대안·소스·모션·근거 검사기. ‘다른 표현’, ‘더 쉽게’, ‘같은 소스 재사용’, ‘자료 추가’, ‘이 장면만 다시 제안’, ‘확정/잠금’을 제공한다.

하단: P2부터 음성 파형과 간단한 장면 스트립을 둔다. Premiere와 같은 범용 다층 타임라인을 처음부터 만들지 않는다.

전체 보기에서는 화면 처리의 반복, 한 장면에 몰린 글, 추가 제작이 필요한 소스, 근거 누락을 보도록 한다. ‘10초마다 반드시 컷’ 같은 규칙 대신 경고와 선택권을 제공한다.

## 6. 데이터 모델 — 화면 종류 한 칸으로 해결하지 않는다

‘실사’, ‘카툰’, ‘모션그래픽’, ‘근거 자료’, ‘하이브리드’는 같은 분류 축이 아니다. 카툰 캐릭터에 모션을 줄 수 있고 실사 위에 실제 근거·숫자 그래픽을 동시에 배치할 수 있다.

분리할 축은 다음과 같다.

| 축 | 예시 |
|---|---|
| 설명 역할 | 맥락, 비교, 과정, 감정, 근거 |
| 확보 방법 | 업로드, 스톡 검색, 직접 캡처, 생성, 직접 제작 |
| 미디어 유형 | 영상, 이미지, SVG, 음성, 데이터 |
| 구성과 움직임 | 카드 축적, 비교표, 화면 강조, 캐릭터 반응; 시작→변화→끝 |

장면은 `layers[]`로 표현한다. 예: 아래 실사 영상, 중간 결제 카드, 위 핵심 문구. `hybrid`라는 단어만 출력하지 않는다.

중심 엔티티는 Project, ScriptRevision, ScriptSegment, Beat, Claim, Evidence, SceneGroup, ScenePlan, Candidate, AssetRequirement, Asset, TemplateVersion, NarrationTake, Alignment, CompiledTimeline, DecisionPatch, Run, ExportManifest다. 엔티티를 처음부터 모두 별도 서비스로 분리하라는 뜻은 아니다.

`id`는 순서와 분리한다. 장면 번호가 바뀌어도 자산·음성·결정 연결을 잃지 않도록 한다. `schemaVersion`은 파일 구조 버전, `revision`은 사용자의 편집 버전이다. 생성 작업은 입력 리비전·원문 해시·모델 식별자·프롬프트 버전·템플릿 버전을 기록한다.

이 패키지의 JSON 규격은 전체 도메인 중 **장면 계획 교환과 검증에 필요한 축소 규격**이다. 작업 DB, 다중 테이크, 전환 겹침, 전체 렌더 AST, 원문 리비전 계보, 신뢰할 수 있는 승인 서명은 구현 대상이다. 예시의 후보·템플릿 ID는 설계용이며 원본 프로젝트에 이미 존재하는 기능명이 아니다.

## 7. Director의 작업 분할

초기에는 여러 에이전트 서버 대신 두 번의 제한된 모델 호출과 일반 코드 검증으로 시작한다.

1. 의미 분석: 승인된 발화 구간 ID, 요점, 논리 연결, 사실 검토 필요 여부를 만든다.
2. 표현 제안: 프로젝트 스타일, 실제 템플릿 레지스트리, 기존 자산 목록, 앞뒤 장면 목표를 보고 후보를 만든다.
3. 코드 검증: JSON 규격, 참조 ID, 원문 보존, 존재하는 템플릿, 허용 속성, 예산 범위를 검사한다.
4. 확보 확인: 필요한 경우 공식 검색 API나 수동 입력으로 소스 후보를 연결한다.
5. 선택적 수정: 실패한 구간만 한 번 보정하거나 사람에게 표시한다. 무한 자기검토 루프를 두지 않는다.
6. 사람 확정: 후보를 승인한 다음에만 실제 자산 생성·다운로드·렌더 단계로 넘어간다.

소스 목록에 없는 자산 ID나 존재하지 않는 URL은 거부한다. LLM이 ‘정확성 95점’ 같은 자기 평가를 내놓아도 승인 근거로 사용하지 않는다. 의미 전달력은 사용자 비교와 평가셋으로 측정하고, 구조적 오류는 코드로 검사한다.

원문·웹 페이지·자막·소스 설명은 모두 데이터다. 그 안의 명령이 도구 권한·예산·승인 정책을 바꾸지 못하게 한다.

## 8. 재사용과 시각 문법

초기 템플릿은 여섯 계열로 제한한다: 실사+설명, 카드 축적, 좌우 비교, 과정 도식, 자료 화면 강조, 고정 캐릭터 반응. 사실 데이터 차트는 근거 테이블 연결을 구현한 뒤 추가한다.

각 템플릿은 ID, 버전, 허용 props, 최대 요소 수, 글자 길이/줄 수 제약, 화면비 대응, 최소 읽기 시간, 모션 규칙을 갖는다. 프롬프트로 완전한 TSX/JavaScript를 매번 만들지 않는다. 검토한 컴포넌트에 검증된 데이터만 넣는다. 텍스트는 HTML로 실행하지 않고, SVG 업로드는 별도 정제한다.

`SceneGroup`에는 같은 객체 ID와 스타일을 유지한다. ‘카드 등장→모두 합산→미사용 항목 강조’처럼 한 그래픽을 발전시킨다. 이전 장면의 모든 픽셀에 의존하는 대신 공통 객체 상태를 버전별 스냅샷으로 보관해 순환 참조·연쇄 실패를 피한다.

‘모아보세요’라는 발화에 카드 등장, ‘합쳐’에 그룹 묶기처럼 모션을 발화 구간/문구에 연결한다. 초기에는 임시 위치로 보여주고 음성 확정 뒤 프레임 위치로 변환한다.

한 프로젝트의 글꼴, 강조색, 기본 여백, 자막 영역, 움직임의 세기를 스타일 프리셋으로 고정한다. 어떤 원본 채널의 스타일을 그대로 복제했다는 주장은 하지 않는다.

## 9. 자산 검색·근거·이용 조건

최초 제공자는 파일 업로드와 사용자가 직접 캡처한 자료다. 다음 단계에 Pexels 하나만 추가한다. 스톡 소스 전체를 긁어 독자 라이브러리로 만드는 것은 범위에서 제외한다.

조회 단위는 ‘해당 장면의 자산 요구’다. 검색어는 대상+행동+구도+여백 조건으로 만들고, 결과는 실제 API 반환 ID를 유지한다. 전체 해상도 다운로드 전에 메타데이터·썸네일로 검토한다. 필요한 구간 길이, 화면비/크롭 가능성, 자막 위치와 인물/물체 겹침, 행동의 시작/끝을 사람이 확인한다.

한 자산에는 제공자, 제공자 ID, 원문 URL, 저자, 확인 시점, 사용 조건 링크, 해당 용도의 승인/보류 결정, 크레딧 문구, 원본 파일 해시를 저장한다. API 검색 결과와 내 서버 파일의 이용 권한을 혼동하지 않는다.

Pexels 공식 API는 플랫폼/기여자 표시와 호출 제한을 안내한다. 공식 안내는 무단 대량·체계적 복제, 경쟁 서비스 구성, API를 통한 대규모 ML/AI 데이터 수집도 제한한다. 따라서 자동 크롤링·대량 임베딩 인덱스는 기본 기능으로 만들지 않는다. 선택 자산을 외부 AI에 전송하는 분석 기능도 별도 권한 확인 전에는 꺼 둔다. [S17, S18]

사실 근거는 자산 라이선스와 분리한다. 공개 보고서는 사실을 뒷받침할 수 있지만 본문 전체를 영상에 재배포할 권한을 자동으로 주지 않는다. 반대로 사용 허용된 스톡 영상이 특정 사건·서비스의 증거가 되는 것도 아니다. 인물·상표 등 제3자 권리 확인은 파일 라이선스만으로 끝났다고 표시하지 않는다. [S19]

근거가 필요한 수치는 `Claim→Evidence→원문 위치/기간/단위`로 연결한다. 데이터 차트의 출력은 이 연결이 없는 상태에서는 워터마크가 있는 초안/더미로만 허용한다. ‘근거를 사람이 검토한 기록이 있음’과 ‘사실이 절대적으로 증명됨’을 구별한다.

## 10. 음성과 시간

장면마다 별개의 TTS 음성을 무조건 생성하지 않는다. 기본은 단락/장 단위 내레이션 트랙과 그 위에 독립적인 화면 컷이다. 일부 문장이 고쳐져도 전체 음성을 다시 생성하지 않도록 테이크를 구간별로 버전 관리한다.

글자 수 기반 길이는 초기 대략치로만 사용한다. 최종 음성의 실제 길이와 발화 정렬을 기준으로 한다. 한국어 수치, 단위, 영어 약어, 괄호를 읽는 방식은 숫자가 보이는 대본과 실제 발음이 다를 수 있으므로 원문 표기와 음성 정렬용 표기를 분리하고 사람이 보정할 수 있어야 한다.

최종 컴파일은 정수 프레임 기반으로 수행한다. 하나의 기준 fps/시간축에서 컷, 자막, 효과, 전환을 계산한다. MVP 교환 예시는 겹침 없는 순차 장면만 허용한다. 전환 겹침과 복합 오디오 트랙은 나중에 별도 규격으로 늘린다.

내레이션 변경은 해당 음성·정렬·컴파일 결과를 무효화한다. 색상 변경은 음성을 무효화하지 않는다. 소스 교체는 해당 장면 렌더와 사용 조건 확인만 갱신한다. 변경 종류별 영향 표를 도메인 규칙으로 만든다.

## 11. 기술 구조

초기 권장 구성은 기존 Next/React 셸 + 새로운 TypeScript 도메인 모듈 + SQLite + 로컬 파일 저장 + 별도 Node 작업 프로세스다. 원본 프로젝트의 브라우저 IndexedDB를 영구 원장으로 사용하지 않는다. IndexedDB는 미리보기 캐시와 임시 UI 상태로 제한한다. [S4, S5]

```text
apps/web 또는 기존 app/
  studio/               대본·장면표·대안 UI
  api/projects/         프로젝트·리비전 CRUD
  api/plans/            생성 요청·패치 승인
  api/assets/           검색·수집 요청
  api/runs/             상태·이벤트·취소
lib/domain/
  script/ beats/ scenes/ assets/ evidence/ revisions/
lib/director/
  analyze/ propose/ repair/ validate/
lib/templates/
  registry/ props-schemas/ motion-recipes/
lib/storage/
  sqlite/ filesystem/ migrations/
workers/
  planner/ asset-ingest/ audio/ render/
```

이 폴더는 신설 제안이다. 초기에는 monorepo 도구 없이 한 저장소로 시작해도 된다. React 화면과 Svelte 화면을 억지로 결합하거나, Python/Express/FastAPI를 동시에 운영할 이유는 없다.

### API 계약 예시

- `POST /api/projects`: 프로젝트와 초기 대본 리비전 생성.
- `POST /api/projects/:id/plans`: `{baseRevision, scope, presetId}`를 받아 `202 {runId}` 반환.
- `GET /api/runs/:id/events`: 작업 상태를 SSE로 전송; 마지막 이벤트 이후 재연결 지원.
- `PATCH /api/projects/:id/scenes/:sceneId`: `{baseRevision, changes}` 검증, 잠금 확인, 리비전 충돌은 409.
- `POST /api/projects/:id/script-proposals/:proposalId/accept`: 승인 시 새 대본 리비전 및 영향 범위 기록.
- `POST /api/runs/:id/cancel`: 작업 취소 요청. 실행·과금이 이미 발생했으면 취소가 환불을 의미하지 않음.

생성 응답은 곧바로 사용자 편집본을 덮어쓰지 않는다. 입력 당시 리비전에 연결된 후보로 저장하고 적용은 패치 경로로만 한다.

## 12. 신뢰성·비용·보안

작업 원장은 입력 해시, 입력 리비전, 모델·프롬프트 버전, 제공자 요청 ID, 예상 비용, 실제 사용량, 상태와 산출물 ID를 기록한다. 제공자가 지원하는 경우 idempotency key를 사용한다. 네트워크 타임아웃으로 결과를 알 수 없을 때 즉시 새 유료 요청을 보내지 않고 기존 요청 상태를 먼저 조회한다.

상태 전이에는 `queued→running→succeeded/failed/cancelled` 외에 제공자 결과가 불분명한 `reconciling`을 둔다. 취소 이후 늦게 도착한 성공 응답이 사용자 결과를 다시 확정하지 않도록 작업 세대 번호 또는 fencing token을 사용한다. 워커 동시 실행 수와 재시도 횟수를 제한한다. 장시간 작업을 단일 웹 요청에 묶지 않는다.

API 비용과 사람의 작업 부담은 서로 다른 항목으로 보인다. 비용을 모르면 0원이 아니라 ‘미산정’이다. 단가표는 확인 시각·버전·통화를 포함하고 예산 승인을 받는다. 이미 가진 소스와 템플릿의 재사용 여부를 작업 부담의 주요 근거로 삼되 고정 별점으로 전달력을 단정하지 않는다.

로컬 기본 바인딩은 127.0.0.1이다. 로컬에서도 Origin/CSRF 확인, 접근 토큰, 파일 경로 제한을 적용한다. API 키는 서버 환경 또는 별도 비밀 저장소에서만 다루고 로그·작업 결과·ZIP에 기록하지 않는다. 원본의 암호화된 키 쿠키를 ‘다중 사용자 로그인 구현’으로 오해하지 않는다. [S5]

미디어 URL 수집은 허용 제공자/호스트, 리디렉션 후 재검사, 사설 IP·로컬 메타데이터 주소 차단, 확장자/MIME/크기 검사, 제한 시간과 다운로드 상한을 둔다. 업로드 SVG/HTML/미디어 메타데이터는 신뢰하지 않는다. 모델의 임의 코드 실행은 MVP에서 제공하지 않는다.

클라우드 SaaS로 바꿀 때에는 별도의 로그인·소유권·테넌트 격리·작업별 권한·외부 객체 저장·삭제/보관 정책이 추가되어야 한다. 로컬 SQLite/파일 저장을 일반 서버리스 함수의 임시 디스크에 그대로 옮기는 설계는 하지 않는다.

## 13. 렌더와 내보내기

P1 출력은 canonical JSON, 사람이 읽는 장면표 CSV/Markdown, 소스 요구 목록과 프롬프트 팩이다. P2는 임시 음성이 포함된 애니매틱. P3에 검토된 템플릿 컴포넌트로 최종 영상 렌더를 추가한다.

Remotion은 React 미리보기/렌더 어댑터 후보다. 엔진 버전과 사용 조건을 고정해 확인하고, 사용자·조직·서비스 형태가 달라지면 재검토한다. Code2MP4의 HyperFrames/HTML 계열은 다른 후보지만 두 엔진을 동시에 도입하지 않는다. [S10, S14, S15, S20]

렌더 재현성은 입력 자산 해시·코드/폰트/템플릿 버전·fps·환경을 고정하는 것을 뜻한다. 다른 플랫폼에서도 MP4 바이트가 항상 완전히 같다고 보증하지 않는다.

SRT는 실제 또는 검토된 음성 정렬 이후 내보낸다. 추정 타이밍 산출물은 명시적으로 초안으로 표시한다. 향후 OTIO는 컷·길이·미디어 참조 교환에 사용하되 내부 모션 컴포넌트가 다른 편집기로 그대로 옮겨진다고 약속하지 않는다. 복잡한 그래픽은 영상으로 렌더하고 소스는 별도 파일로 보관한다. 특정 편집기 연결은 어댑터별 실제 테스트가 필요하다. [S21]

## 14. 구현 순서와 완료 기준

### P0 — 포크 기반과 규격

라이선스·출처를 기록하고 원본 버전/lockfile을 보존한다. 기존 채팅/생성 UI와 새로운 studio를 분리한다. 새 도메인 규격, 승인·잠금·리비전, 테스트 fixture를 만든다. 외부 유료 호출 없이 계획 데이터를 불러오고 저장할 수 있어야 한다.

### P1 — 사용할 수 있는 장면 설계 도구

한국어 대본 입력, 원문 연결, 의미 단위, 두 가지 표현 대안, 시작/변화/끝, 화면 재사용, 대본 수정 diff, 장면별 직접 편집/확정/잠금, 계획 JSON/CSV와 미해결 자산 목록이 범위다. 초기 소스는 수동 업로드와 확보 지시다. MVP의 핵심 완료 조건은 생성 결과를 복사해 다시 손질하는 것이 아니라 앱 안에서 장면표를 확정할 수 있는 것이다.

### P2 — 소스 확보와 시간 있는 미리보기

Pexels 검색/출처 표시/필요한 파일만 수집, 실제 자료 등록, 이용 조건 기록, 임시/업로드 음성, 애니매틱, bounded worker, 재개·취소·예산 승인 기능을 구현한다. 선택한 소스와 소스 요구가 구분되어야 한다.

### P3 — 확정 렌더와 편집기 교환

여섯 템플릿의 실제 컴포넌트, 다층 합성, 한글 줄바꿈/자막 여백, 음성 정렬 검토, 확정 영상, SRT 및 제한된 편집기 교환을 추가한다. 새 템플릿은 구조 검증과 시각 회귀 테스트를 통과한 뒤 레지스트리에 등록한다.

자세한 이슈 단위 작업과 의존 관계는 `BACKLOG.md`에 있다. 일정·구현 소요 시간은 코드 실행 기준선이 없는 현재 조사에서 산정하지 않았다.

## 15. 검증과 이 패키지의 한계

이 패키지에는 직접 작성한 JSON Schema, 템플릿 props 규격, 3장면 가상 예시, Python 참조 검증기와 23개 합성 테스트가 있다. 규격 자체, 원문 해시/연결, 잘못된 템플릿/속성, 미확보 소스, 승인·잠금, 리비전 충돌, 프레임 공백, 오래된 음성 정렬 등을 검사했다. `test-results.txt`에 실제 실행 결과가 있다.

이 검증기는 원격 API·실제 미디어·법률적 권한·화면 품질·한국어 음성 품질을 확인하지 않는다. `--publish`는 승인 관련 데이터 기록을 검사하는 규칙이며 발행 버튼도, 실제 법적 검증기도 아니다. 템플릿 레지스트리는 허용 데이터 규격일 뿐 렌더 컴포넌트 구현이 아니다.

초기 제품 평가에는 비교 설명, 숫자/단위, 근거 누락, 긴 문장, 감정 비유, 희소한 실사, 재사용 연쇄, 중간 수정, 파일 소실, 취소/재시도 등 서로 다른 한국어 시나리오를 넣는다. 모델의 자기 점수 대신 실제 사용자 승인 결과와 수정량을 기록한다.

**첫 구현 목표: 대본을 입력하고 화면 대안 두 개를 비교한 뒤, 한 장면만 고쳐도 나머지 확정 작업이 보존되는 편집 경험.**
